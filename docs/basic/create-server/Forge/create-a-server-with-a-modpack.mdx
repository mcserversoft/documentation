title: "Run a modpack server"
description: "Preserve the pack\u2019s installer, dependencies, and launch arguments instead of rebuilding its startup script."
---

Use the pack author's **server pack** for the exact release you want. A client export is not necessarily a complete dedicated server, and not every pack publishes server files.

## Prepare the pack

1. Read the pack's installation and Java requirements.
2. Extract its server archive into a new staging folder outside your active MCSS server directory.
3. Run only the setup or installation steps the author specifies. Let them download the required loader and libraries.
4. Start the pack using its supplied method, complete the EULA step if you agree, and stop it normally.
5. Keep a copy of that working setup before adapting its launcher for MCSS.

This separates a pack installation problem from an MCSS launch configuration problem.

## A pack with a batch launcher [#-step-2]

Inspect the file that actually starts Java. Some packs use one batch file for setup and another for normal starts; follow the author's distinction.

For a straightforward Forge or NeoForge launcher, use MCSS's batch-file launch method and the [generated-launcher checks](/basic/create-server/Forge/create-forge-server-manually#review-a-generated-batch-launcher). Keep argument files, relative paths, and environment variables that the launcher needs. Remove an interactive `pause` from the file used by MCSS where necessary.

Memory may be configured in `user_jvm_args.txt`, another pack configuration file, or the command itself. Change the setting read by **this** pack; do not add competing `-Xmx` values in multiple places.

<Callout type="warn" title="Keep installation logic intact">
Do not replace an arbitrary launcher with a one-line `java -jar server.jar` command. That can omit loader arguments, dependency downloads, or pack-specific setup. Keep Java and dependency checks unless the pack author explicitly documents how to use an externally managed runtime.
</Callout>

## A pack with PowerShell or another setup tool [#-step-3]

Use the pack's documented setup procedure. Do not disable PowerShell restrictions or Java checks just to make a generic template run.

If the setup produces a Windows batch launcher, use that generated launcher. If it does not, identify the supported normal-start command from the pack's documentation before configuring MCSS. Copying variable names from another pack is not enough to reconstruct it.

## Import and verify

[Import the complete directory](/basic/import-server/supported-server-files), select the appropriate executable or launcher, and confirm that all relative library paths still resolve after import.

Start the imported copy and check the Minecraft version, loader version, mod loading, world, and player data. Test using the **same pack release** on the client. Keep the original staging folder until these checks pass.

## Update the pack as a unit

Use the author's server update instructions and take a [full backup](/backups/backup-and-restore). Test a copy before changing the live server. Do not individually update the loader or every mod to its newest release unless the pack author supports that combination.
